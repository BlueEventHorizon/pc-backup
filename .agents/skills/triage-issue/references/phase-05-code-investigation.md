# Phase 5: 既存コード調査ルール

Grep / Glob（および利用可能であれば Serena MCP 等のコードシンボル検索ツール）を使い、実装に再利用できる既存クラス・コンポーネント・ユーティリティを特定する。

このフェーズの本質は「既存資産を徹底的に洗い出すこと」。表面的な検索で済ませず、判定（Blast Radius の実測）と実装工程への引き継ぎに耐える粒度で特定する。特定した資産をどう使うか（改修 / 流用 / 新規作成の判断）は実装工程（`impl-issue` Phase 5〜8）の責務。

## 探索対象

以下を網羅的に探索し、見つかったものをパスと一言メモ（何に使えそうか）で記録する。**見つからなかった場合も「該当なし」を記録する**（実装工程が「未調査」と区別できるようにするため）:

- **同一目的の状態管理・Provider・Notifier**: 機能名（「並び順」「ソート」「フィルタ」「リスト状態」等）で全体 Grep
- **同一目的のドメインモデル / enum / 値オブジェクト**: プロジェクトのドメインモデル配置場所（`/forge:query-db-rules` で「ディレクトリ構造」を検索）を Glob / Grep
- **同じ場所の既存ファイル（仮実装含む）**: 同名ファイルの有無
- **兄弟機能（同種パターンを持つ他画面・他機能）の実装**: 同種の画面・機能（一覧、詳細、フォーム等）の既存実装を **3 件以上** 特定する。特に **直近マージ・直近進行中の PR** で確立されたパターンを重視し、`git log` で最近の変更を確認する
- **既存 extension / utility / helper**
- **i18n / debug / route エントリ**: 既に登録済みの口がないか
- **共通コンポーネント**: 配置先はプロジェクト規約から取得（`/forge:query-db-rules` で「ディレクトリ構造」「共通コンポーネント」を検索）

## その他の調査ポイント

- 同じドメイン領域の既存モデル・リポジトリ・状態管理
- 実装の参考になる類似のユースケース層
- クラス・インターフェースのシグネチャ、命名規則・ファイル配置パターン
- 動作確認手段があるか（debug 画面・カタログ等のプロジェクト固有導線）
